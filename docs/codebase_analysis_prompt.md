## 1. Operating Constraints

1. **Read-only by default.** Treat the audit as a static analysis pass.
   Use grep/ripgrep, AST-level inspection, and (optionally) a disposable
   bench site for runtime verification. Never modify production data.
2. **Cite every finding** with a code reference in the form
   `path/to/file.py:LINE` (or a line range). A finding without a citation
   is invalid.
3. **Quantify wherever possible.** Counts, percentages, query timings,
   number of `frappe.db.sql` calls per request, etc. Vague adjectives
   ("some", "a lot") are not acceptable.
4. **Prefer Frappe-idiomatic recommendations.** Solutions must use
   Frappe v15 APIs (`frappe.qb`, `frappe.get_all`, `frappe.cache`,
   `frappe.enqueue`, `Document` lifecycle hooks, child-table helpers,
   `validate_workflow`, `frappe.utils.background_jobs`, etc.) — not
   bespoke reimplementations.
5. **Respect the dual-module split.** Always state whether a finding
   belongs to the `jewellery_erpnext` module, the `gurukrupa_exports`
   module, or to cross-cutting top-level files (`hooks.py`,
   `interbranch.py`, `query.py`, `utils.py`, `erpnext_override.py`).
6. **Treat ERPNext core overrides as high-risk.** Anything touching
   `Stock Entry`, `Stock Ledger Entry`, `Serial and Batch Bundle`,
   `Stock Reconciliation`, `BOM`, `Work Order`, `Job Card`,
   `Material Request`, `Purchase Receipt`, `Sales Invoice`,
   `Payment Entry` must be evaluated for correctness against the
   corresponding ERPNext v15 base class behavior, including transaction
   integrity and stock ledger consistency.

## 3. Phase 1 — Comprehensive Code Review

### 3.1 Code structure examination

Evaluate the organization against Frappe v15 layout conventions:

- App skeleton: `pyproject.toml`, `setup.py`, `MANIFEST.in`, `hooks.py`,
  `modules.txt`, `patches.txt`, `requirements.txt`, `public/`,
  `fixtures/`, `templates/`.
- Module folder: `<app>/<module>/doctype/<doctype>/<doctype>.{json,py,js}`
  with optional `test_<doctype>.py` and reports/dashboards/page subfolders.
- Identify **structural smells**:
  - Top-level helper modules (`utils.py`, `query.py`, `interbranch.py`)
    that bypass the module/doctype layout — decide which deserve to be
    promoted into a proper sub-package (e.g. `utils/`).
  - Code under `customization/` that duplicates files under
    `doc_events/` (e.g. multiple before_validate callbacks for
    `Stock Entry`, `Sales Invoice`, `Material Request`, `Sales Order`,
    `Purchase Receipt`); decide whether the split is intentional or a
    refactor scar.
  - DocType folders with empty/stub `.py` controllers — do they need
    behavior, or should they stay declarative?
  - Naming inconsistencies: `recoverd_diamond` vs `recovered_diamond`,
    `recoverd_gemstone` vs `recovered_gemstone`,
    `child_stock_reconcilation` (typo) — flag, propose rename via
    `frappe.rename_doc` patch.
  - Cross-module imports (does `gurukrupa_exports` reach into
    `jewellery_erpnext` or vice-versa?). Map the dependency graph.
- Best-practice scoring: assign each module a score (1–5) for layout,
  cohesion, separation of concerns, and naming consistency; back each
  score with two citations.

### 3.2 Functionality breakdown

For every public function in `doc_events/`, `customization/`,
`erpnext_override.py`, `interbranch.py`, `query.py`, `utils.py`,
`migrate.py`, and the `jobs/` package:

- Document **Inputs** (with types — read from type hints or infer from
  call sites), **Side effects** (DB writes, `frappe.msgprint`, network
  I/O, file system), **Returns**, and **Exceptions** raised.
- Confirm that the function name, location, and registered hook agree
  on its purpose.
- Detect **lifecycle misuse**: e.g. mutating the document in
  `on_submit` instead of `before_submit`, calling `db_set` outside an
  `on_update_after_submit` context, or using `validate` for irreversible
  side effects.

### 3.3 Use of Frappe APIs and utilities

For each Python file in scope, check:

- **ORM**: prefer `frappe.qb` / `frappe.get_all` / `frappe.db.get_value`
  over `frappe.db.sql`. Flag every raw SQL call and decide whether it
  is justified (complex aggregation, window functions) or could be
  replaced.
- **Document API**: prefer `doc.append`, `doc.db_set`, `doc.run_method`,
  `doc.flags`, and child-table iteration; flag direct list mutation
  that bypasses Frappe’s child-row plumbing.
- **Caching**: identify hot paths that recompute the same lookups and
  recommend `frappe.cache().hget/hset` or
  `@frappe.utils.caching.redis_cache` with sensible TTLs.
- **Background jobs**: anything user-facing that runs > 200 ms should
  be enqueued via `frappe.enqueue` with an appropriate `queue` and
  `job_name` (so duplicates are coalesced).
- **Permissions**: every `@frappe.whitelist()` endpoint must declare
  `allow_guest` explicitly (default False) and either rely on doctype
  permissions or call `frappe.has_permission` / `frappe.only_for`
  before performing privileged actions.
- **Validation**: prefer `frappe.throw(_("..."))` with translation and
  a `title=` over plain `raise Exception`; never use `print` for user
  feedback.
- **Translations**: every user-visible string must be wrapped with
  `_()`; flag missing wrappers.
- **Hooks correctness**: confirm each entry in `hooks.py` resolves to
  an importable callable and that the signature matches what Frappe
  passes (e.g. `(doc, method)` for doc_events).

Deliverable for this phase: **Section B** of the final report.

## 11. Acceptance Criteria

1. Every section A–I is present and non-empty.
2. Every finding has a `path:line` citation.
3. The relationship graph (D.1) renders in GitHub Markdown.

   a `delete / keep / replace` verdict each.
5. The performance section (E) contains at least one quantified
   measurement (either static count of N+1 patterns or a runtime
   timing if a bench site is available).
6. The consolidated backlog (I) contains ≥ 20 items, each tagged with
   severity and effort and ranked by ROI.
7. No recommendation breaks Frappe v15 compatibility or violates the
   ERPNext stock ledger invariants.
8. The report is reproducible: every command used to derive a finding
   is included in an appendix so a reviewer can re-run it.
